# /shares P1 批量关闭设计

**目标**

在不扩大 `/shares` 第一版范围的前提下，为分享中心补齐最小可用的批量管理能力：

1. 当前页多选
2. 批量关闭分享
3. 批量关闭前二次确认

这样站长和普通用户在处理一批过期、失效或不再需要的分享时，不必逐条点击关闭，能明显降低操作成本。

## 本轮确认范围

**包含：**

- `/shares` 表格增加当前页多选能力
- 顶部新增“批量关闭”入口
- 批量关闭前统一二次确认
- 批量关闭后提示成功/失败数量
- 操作完成后刷新列表并清空当前选择

**不包含：**

- 跨页选择
- 全站全选
- 批量复制链接
- 批量重生成一次性分享
- 通用 `Table` 组件升级为 selectable table
- 后端新增批量关闭接口

## 方案对比

### 方案 A：前端当前页批量关闭，逐条调用现有关闭接口

**优点：**

- 改动最小，直接复用现有分享关闭接口
- 不需要改动通用 `Table` 组件
- 前端交互可直接复用 `Audit.vue` 的选择模式
- 风险低，最符合本轮 KISS / YAGNI

**缺点：**

- 一次批量操作会发起多次请求
- 无法天然保证服务端原子性

### 方案 B：新增 `/api/shares/batch-disable` 后端接口

**优点：**

- 批量语义更清晰
- 后续更容易扩展批量审计、批量结果结构

**缺点：**

- 需要新增路由、参数校验、权限处理和测试
- 当前需求只是 `/shares` 第一版体验补齐，投入偏重

### 方案 C：先抽象通用 selectable `Table`

**优点：**

- 后续其它页面也可复用

**缺点：**

- 当前项目只有 `Audit.vue` 有成熟的选择模式
- 会把本轮从页面增强扩大为组件级重构
- 明显超出本轮必要范围

**结论：采用方案 A。**

## 详细设计

### 1. 交互范围

批量操作只对**当前页已勾选记录**生效：

- 左侧增加 checkbox 列
- 表头支持当前页全选 / 取消全选
- 顶部显示批量关闭按钮，并带上当前选择数量

例如：

- `批量关闭（0）`
- `批量关闭（3）`

当没有选择项时，按钮禁用。

### 2. 选择状态模型

不改通用 `Table` 组件，直接在 `Shares.vue` 内复用 `Audit.vue` 的模式：

- `selectedIds`
- `pageRowIds`
- `selectedIdSet`
- `allRowsSelected`
- `someRowsSelected`
- `selectAllIndeterminate`

这里的“选择 id”不直接用分享表主键，而使用当前列表可稳定唯一标识一行的组合键，例如：

- `type + resource_id`

原因：

- `/shares` 当前聚合列表并没有对前端暴露统一 share id
- 现有单条关闭动作本来就是按 `type + resource_id` 分流到不同接口
- 这样能避免为了批量关闭单独改后端返回结构

### 3. 批量关闭按钮与确认弹窗

页面顶部新增批量按钮：

- 文案：`批量关闭（{count}）`
- 危险态按钮

点击后先打开统一确认弹窗，不直接执行。

确认弹窗文案需要明确：

- 会关闭所选分享
- 关闭后这些链接将不可访问
- 本次操作记录数

本轮继续复用 `Shares.vue` 现有确认弹窗机制，不新增第二套 modal。

建议把待确认动作扩展为：

- 单条关闭
- 单条重生成
- 批量关闭

由统一计算逻辑输出：

- 标题
- 正文
- 按钮文案
- 按钮类型

### 4. 批量执行策略

批量关闭时不新增后端接口，而是前端按记录类型逐条调用现有接口：

- `file` -> `api.deleteFileShare(resource_id)`
- `text` -> `api.deleteTextShare(resource_id)`
- `text_one_time` -> `api.deleteTextOneTimeShare(resource_id)`

执行方式建议：

- 用 `Promise.allSettled`
- 统一统计成功数 / 失败数

原因：

- 某条记录失败不应阻塞其它记录关闭
- 结果汇总更适合批量操作反馈

### 5. 批量执行中的禁用规则

批量关闭提交期间，页面进入“批量操作中”状态：

- 顶部批量关闭按钮禁用并显示 loading
- 行级关闭 / 重生成 / 编辑按钮禁用
- checkbox 禁用
- 搜索 / 刷新按钮维持现有 `loading` 约束

目标是避免：

- 同一批记录重复提交
- 行级操作与批量操作并发
- 提交中修改勾选状态造成语义混乱

### 6. 列表刷新与选择清理

批量关闭完成后：

1. 关闭确认弹窗
2. 清空当前选择
3. 刷新列表
4. 若当前页因关闭后为空且页码大于 1，复用现有 `loadShares()` 的页码修正逻辑

以下场景也应清空选择：

- 搜索
- 刷新
- 翻页
- 修改每页数量

这样可保证“选择集合”和“当前页数据”始终一致。

### 7. 成功 / 失败提示

批量关闭完成后按结果提示：

- 全部成功：提示关闭成功数量
- 部分成功：提示成功数量 + 失败数量
- 全部失败：提示批量关闭失败

不在本轮展示失败明细列表，也不做失败重试流程。

这符合第一版最小可用原则。

### 8. 代码组织建议

为保持 `Shares.vue` 可维护性，推荐把与批量关闭相关的纯逻辑下沉到 `frontend/src/utils/shares.js`：

- 生成行选择 key
- 从选中集合中过滤可执行记录
- 批量结果文案元信息

但仍保持 YAGNI：

- 只抽真正重复或可测的纯逻辑
- 不引入新的 composable
- 不抽象成通用表格选择模块

### 9. 文案与国际化

需要同时补齐中英文：

- 批量关闭按钮文案
- 批量关闭确认标题 / 正文
- 批量关闭成功 / 部分成功 / 失败提示
- 选择列标题（若需要）

## 测试策略

### 前端单测

在 `frontend/tests/shares-utils.test.js` 增加最小纯函数测试，优先覆盖：

- 行选择 key 生成稳定
- 选中记录过滤逻辑
- 批量关闭结果摘要逻辑

### 前端验证

至少运行：

- `node --test "frontend/tests/shares-utils.test.js"`
- `npm --prefix "frontend" run lint"`
- `npm --prefix "frontend" run build`

### 后端

本轮不新增后端接口，因此**不要求新增 worker 测试**。

## 风险与控制

### 风险 1：批量关闭过程中部分请求失败

**控制：** 使用 `Promise.allSettled`，允许部分成功，并明确反馈成功/失败数量。

### 风险 2：翻页后仍保留旧选择，导致误操作

**控制：** 搜索、刷新、翻页、改 page size 后统一清空选择。

### 风险 3：为了批量选择而改通用 `Table`，引入额外回归

**控制：** 本轮只在 `Shares.vue` 局部实现 checkbox 列，不改 `Table` 组件。

## 验收标准

- `/shares` 支持当前页多选
- 支持当前页全选 / 取消全选
- 顶部可对已选记录执行批量关闭
- 批量关闭前必须二次确认
- 批量关闭后能清晰反馈成功 / 失败数量
- 操作完成后列表刷新且选择被清空
- 单条复制、打开、编辑、关闭、重生成能力不回归
