# Security Hardening Phase 2 Design

**日期：** 2026-04-09

## 目标
第二批整改聚焦两件事：

1. 以**保守升级**方式处理高风险运行时依赖，并顺手消化可无痛修复的开发依赖告警。
2. 修复上传链路的**并发配额绕过**问题，将现有“事后统计”模式改为“预先原子占用 + 成功结转 + 失败释放”的模型。

本阶段遵循 KISS / YAGNI：不做大重构，不追求一次性清空所有 audit 告警，不引入复杂 quota ledger，只做能显著降低风险且便于平滑上线的收口。

---

## 约束与确认

已确认的用户约束：
- 依赖升级采用**保守升级**。
- 告警处理范围为：**运行时依赖 + 能无痛修掉的开发依赖**。
- 允许**小幅 schema 变更**。
- 采用**平滑迁移**，兼容旧数据。
- 不主动执行 git 提交、分支或 worktree 流程。

---

## 方案选择

### 备选方案

#### 方案 A：最小修补
- 只升级少量直接依赖。
- 配额仍沿用 `SUM(files.size)` 即时判断，仅增加更多接口层检查。
- 优点：改动最小。
- 缺点：不能真正解决并发超配额。

#### 方案 B：保守但完整（选用）
- 依赖：优先升级高风险运行时依赖，并顺手升级不需要明显适配的开发依赖。
- 配额：在 `users` 表增加预留字段，上传前原子占用，成功后结转，失败后释放。
- 优点：真正解决并发问题，兼容现有架构，风险收益平衡最佳。
- 缺点：需要少量 schema 演进与清理逻辑补偿。

#### 方案 C：彻底重构
- 大范围升级依赖并引入独立 quota ledger / 更复杂状态机。
- 优点：长期最干净。
- 缺点：超出本阶段“保守升级”边界。

### 最终方案
采用 **方案 B**。

## 依赖升级设计

### 前端依赖升级目标
优先处理以下**运行时直接依赖**：
- `axios`
- `dompurify`
- `markdown-it`

对于以下**开发依赖**，仅在可无痛修复时顺手处理：
- `vite`
- 与其联动但不要求明显适配的构建链依赖

原则：
- 优先升级到可修复已知高风险告警的**最小安全版本**。
- 尽量不跨入高破坏大版本。
- 若某升级会引入明显行为变化，则单独评估，不强行合入本批。

### Worker 依赖升级目标
优先处理以下**运行时直接依赖**：
- `@aws-sdk/*`

对于以下**开发依赖**，仅在可无痛修复时顺手处理：
- `wrangler`
- 与已知高风险告警直接相关、且不需要明显适配的开发链依赖

原则同上：
- 先处理运行时直接依赖。
- 对开发依赖，仅修复那些**无需明显适配**的部分。
- 不为了清空 `npm audit` 强行引入大版本重构。

### 依赖升级验收标准
- 运行时高风险告警优先下降。
- `npm audit --audit-level=moderate` 总量明显下降。
- `worker` 的类型检查和 lint 通过。
- `frontend` 的 lint 和 build 通过。
- Markdown 预览、上传、分享等核心能力不回归。

## 上传配额并发修复设计

### 当前问题
现有上传链路在 `presignUpload` / `initMultipart` 中：
1. 先统计用户已用空间
2. 再判断是否超配额
3. 再创建文件记录

这是典型的“先查后写”竞态：多个并发请求可以同时通过检查，导致总占用超过 `quota_bytes`。

### 核心设计
给 `users` 表增加字段：
- `reserved_quota_bytes INTEGER NOT NULL DEFAULT 0`

必要时给 `files` 增加一个最小标记字段，用于表达“当前文件是否仍持有预留额度”，例如：
- `quota_reserved INTEGER NOT NULL DEFAULT 0`

并将配额判定改为：

`completed_usage + reserved_quota_bytes <= quota_bytes`

其中：
- `completed_usage`：当前已完成文件实际占用
- `reserved_quota_bytes`：正在上传且仍持有预留的总占用

### 平滑迁移策略
当前线上语义中，`pending/uploading/completed` 都会计入占用；因此切换到 `completed + reserved` 时，不能让存量未完成上传瞬间脱离统计。

本阶段要求采用以下过渡策略之一，并在 implementation plan 中明确落地：
1. **回填方案**：迁移时将所有仍有效的 `pending/uploading` 文件尺寸汇总并回填到 `reserved_quota_bytes`，同时为对应文件补 `quota_reserved = 1`；或
2. **过渡兼容方案**：在过渡期内，继续把历史 `pending/uploading` 记录纳入有效占用计算，直到这些记录被清理或完成。

推荐优先使用 **回填方案**，因为语义更收敛。

### 生命周期

#### 小文件上传
1. 客户端请求 `presignUpload`
2. 服务端原子增加 `reserved_quota_bytes`
3. 预留成功后创建 `pending` 文件记录
4. 若建记录失败，立即释放预留
5. 客户端上传完成后调用 `confirmUpload`
6. 服务端确认对象存在，文件状态改为 `completed`
7. 释放对应预留占用

#### 分片上传
1. 客户端请求 `initMultipart`
2. 服务端原子增加 `reserved_quota_bytes`
3. 预留成功后创建文件记录并初始化分片上传
4. `completeMultipart` 成功后释放预留
5. `abortMultipart` 或上传失败清理时释放预留

#### 过期/僵尸记录清理
现有基于 `files.expires_at` 的清理不足以覆盖“上传卡死/用户放弃”的场景，尤其永不过期文件可能导致预留永久占住。

因此需要引入独立的**预留过期/上传超时**语义，建议使用以下之一：
- 新增 `reservation_expires_at`；或
- 基于 `created_at/updated_at` 定义 stale timeout（例如超过固定时长仍未完成则回收）

本阶段 implementation plan 必须明确：
- stale timeout 的判定依据
- 哪个定时任务负责回收
- 回收是否幂等

## 数据结构设计

### Schema 变更
在 `users` 表增加：
- `reserved_quota_bytes INTEGER NOT NULL DEFAULT 0`

### 服务层拆分
建议新增一个专职服务，例如：
- `worker/src/services/quotaReservation.ts`

职责限定为：
- 原子预留上传额度
- 释放预留额度
- 在确认上传成功后结转/释放
- 提供统一的“当前有效占用”计算方式

这样避免把配额规则散落到：
- `routes/upload.ts`
- `jobs/cleanupExpired.ts`
- 其他可能的删除/恢复路径

---

## 原子操作语义

### 预留额度
预留动作必须明确其原子边界，并且配额判断必须基于 **数据库当前值**，不能依赖登录态或请求上下文缓存的 `user.quota_bytes`。

本阶段设计要求 implementation plan 至少明确以下之一：
1. **单条条件更新方案**：基于 DB 当前 `users.quota_bytes` 与已完成占用计算结果做条件更新；或
2. **事务方案**：在一个明确事务边界内读取已完成占用、读取用户当前配额与预留、再更新预留。

无论选择哪种实现，必须满足：
- 并发请求不能同时越过同一份剩余额度
- 判断依据来自 DB 当前数据
- 不能继续只依赖外层“先查后写”

### 释放额度
释放时必须：
- 防止减成负数
- 保证幂等，避免重复释放导致保留值异常

本阶段要求有一个**文件级可判定标记**（推荐 `quota_reserved`），用于表达“该文件当前是否仍持有预留额度”。

所有释放操作都应满足类似语义：
- 只有 `quota_reserved = 1` 时才允许释放
- 释放成功后把 `quota_reserved` 置回 `0`
- 重复执行同一路径不会重复扣减 `reserved_quota_bytes`

这样可以让 `confirm/abort/cleanup/delete` 等路径具备统一幂等语义。

## 错误处理设计

### 配额不足
继续返回现有风格错误（如 `413`），不改动前端主交互语义。

### 预留成功但建记录失败
必须立刻回滚释放，避免僵尸预留。

### 上传确认失败
保留预留，等待用户重试确认或由清理任务最终回收。

### 上传取消 / 分片中止
立即释放预留。

### 定时清理
对已过期、已删除、长期未完成的上传记录，统一释放预留。

### 释放路径矩阵（设计约束）
implementation plan 必须逐一覆盖以下路径是否需要释放预留、是否要求幂等：
- `presignUpload` / `initMultipart` 建记录失败回滚
- `confirmUpload` 成功
- `completeMultipart` 成功
- `abortMultipart`
- `cleanupExpired`
- `deleteFile`（若针对未完成上传）
- `deleteUser`（若其名下存在仍持有预留的未完成上传）
- 其他会把未完成上传转为删除/失效状态的路径

术语上统一为：
- **预留**：给 `reserved_quota_bytes` 增加额度
- **释放**：给 `reserved_quota_bytes` 减少额度并清除文件级预留标记
- **完成**：文件进入 `completed`，其大小自然计入 `completed_usage`；此时需要的是“状态切换 + 释放预留”，不引入额外账本“结转”概念

### 服务异常
不要把数据库/对象存储异常伪装成“配额不足”；要区分业务拒绝和服务错误。

## 回归与验证设计

### 静态验证
- `npm audit --audit-level=moderate`
- `npm --prefix worker run typecheck`
- `npm --prefix worker run lint`
- `npm --prefix frontend run lint`
- `npm --prefix frontend run build`

### 业务回归
- 登录/登出
- 小文件上传
- 分片上传
- 取消上传
- 上传确认
- 文本/文件分享基本能力
- Markdown 预览渲染

### 并发配额验证
关键用例：
1. 用户剩余额度 1GB，同时发起两个各 1GB 上传
   - 只能成功一个预留
2. 上传取消后额度恢复
3. 分片初始化后长时间不完成，被清理后额度恢复
4. 已完成文件占用仍计入真实配额

## 非目标
本阶段明确不做：
- 一次性清空所有 `audit` 告警
- 全量依赖大版本升级
- 重新设计整个上传状态机
- 引入独立 quota ledger 系统
- 大规模前端交互改造

---

## 风险与折中

### 依赖升级风险
- 即使保守升级，也可能带来少量 API/构建行为差异。
- 处理方式：优先小步升级并即时验证。

### 预留额度模型风险
- 若释放逻辑不完整，可能出现残留预留。
- 处理方式：由清理任务兜底，并保持释放逻辑幂等。

### 数据迁移风险
- 新字段默认值为 0，可平滑迁移，对现有用户透明。
